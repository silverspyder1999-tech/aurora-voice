A measured review of the live build across both target machines — the GTX 1070 8 GB work PC and the RTX 5080 16 GB home PC. Every number below is measured on-device or extracted from aurora.log; nothing is estimated unless labelled.

SPEC.md acceptance bar A1 is p50 ≤ 700 ms from key-release to text. Across 390 logged dictations on the GTX 1070, not one came in under that bar and the median was 2.16 s. The bar was written against the RTX 5080 and silently carried over to a card that cannot meet it with the current configuration.

2 · Root cause — an eight-day config drift

The dominant cause of the latency tail is not the code. It is that this machine has been running large-v3 on the CPU for every dictation.

The chain

  • config.toml is listed in .gitignore — it is per-machine and never syncs between the two PCs.
  • This machine's config.toml was written 2026-07-04.
  • Commit 1c6d50f (2026-07-12, from the home PC) added the VRAM-aware auto-gate with four new keys: device, cpu_model, gpu_min_free_mib, gpu_poll_s.
  • None of those keys exist in this machine's config, so all four fall back to defaults.
  • gpu_min_free_mib defaults to 4000. Free VRAM on this desktop sits around 3212 MiB. The gate therefore selects CPU.
  • cpu_model defaults to model, so the CPU fallback is large-v3 — measured at RTF 1.93, slower than real time.

The feature built specifically to protect an 8 GB card was shipped from the 16 GB machine and never activated on the machine that needed it.

The structural fix is not "edit the config". It is to stop putting hardware-dependent decisions in an untracked file. A detected hardware profile ships in git; a stale local config cannot then silently disable it. That is section 3.

3 · Dual-hardware support

A single configuration cannot serve both machines — this is a hard constraint, not a preference. CTranslate2 requires compute capability ≥ 7.0 for float16; the GTX 1070 is CC 6.1.

>>> ctranslate2.get_supported_compute_types('cuda')   # GTX 1070, this machine
{'int8_float32', 'int8', 'float32'}                  # float16 is absent

Meanwhile app/config.py still defaults compute_type to "float16" — correct for Blackwell, silently degraded to float32 here (roughly 6 GB, which will not fit alongside a desktop).

Proposed: a detected profile layer

Probe the GPU once at startup and select a built-in preset; config.toml keeps overriding everything, so nothing existing breaks.

# app/profiles.py  (new, ~40 lines)
#   probe: ctranslate2.get_supported_compute_types('cuda') + total VRAM
#   -> pick a preset -> DEFAULTS < preset < config.toml

PROFILES = {
  "pascal-8gb":    dict(compute_type="int8",    model="distil-large-v3",
                        cpu_model="distil-small.en", gpu_min_free_mib=1200,
                        beam_size=1, cleanup_model="qwen3.5:2b"),
  #   NB: gpu_min_free_mib is only safe once the load/release watermarks are
  #   separated (rec 2). distil-large-v3 is 992 MiB, so on a desktop sitting at
  #   ~2.1 GB free it fits and stays; large-v3 at 2008 MiB does not.
  "blackwell-16gb":dict(compute_type="float16", model="large-v3",
                        cpu_model="distil-small.en", gpu_min_free_mib=5200,
                        beam_size=1, cleanup_model="qwen3.5:4b"),
  "cpu-only":      dict(compute_type="int8",    model="distil-small.en",
                        device="cpu", beam_size=1, cleanup_enabled=False),
}

The thresholds are derived from measurement, not guessed: large-v3 int8 occupies 2008 MiB and distil-large-v3 int8 992 MiB, so a 4000 MiB gate is roughly double what the model actually needs and is what forced this machine onto the CPU.

6 · Feature gaps vs. the field

Measured against Wispr Flow, superwhisper, VoiceInk, Handy, WhisperWriter, Talon/Cursorless, Dragon and Windows Voice Access.

Where Aurora is genuinely ahead

Worth stating plainly, because three of these are things nobody else in the survey does at all:

  • Re-focusing the original dictation target before injecting. capture_target() / restore_target() with AttachThreadInput to defeat the Win32 foreground lock. This solves the field's single most-reported bug class — text landing in the wrong window. Handy's most-commented open issue (56 comments) is exactly this. No other tool surveyed does it.
  • Clipboard snapshot and restore with contention retry and a typing fallback. VoiceInk added this only after complaints; Handy still lacks it.
  • Watchdog + heartbeat + single-instance mutex. The only tool surveyed that self-heals. A comparable project has five separate "silently stops working" issues open.
  • Cleanup guardrails that fall back to raw text — preventing the exact bug VoiceInk shipped twice (LLM answering the dictation instead of cleaning it).
  • Per-app profiles that disable cleanup for code and terminals, a correct streaming implementation, and an overlay that is better craft than anything in the field.

The structural gap

You cannot fix anything by voice. Aurora's entire editing vocabulary is ctrl+z. Every serious tool has converged on speaking at existing text to change it — Wispr's Command Mode, Dragon's Select-and-Say, Cursorless, Voice Access's correction commands. This is the one feature that separates a dictation toy from a dictation tool, and it is the loudest unmet demand in user discussion.

10 · Method & caveats

  • Telemetry — 390 dictations parsed from aurora.log (2026-07-04 → 2026-07-25). Percentiles are nearest-rank.
  • Benchmarks — run on this GTX 1070 against test.wav. Clips beyond 11.26 s were built by tiling that file, so the 30 s instant-mode figure is synthetic; the ~5 s crossover is a clean measurement and is the number to plan against.
  • RTX 5080 figures come from PHASE0_REPORT.md (2026-07-03), not re-measured in this pass.
  • Not measured: large-v3-turbo — the distil-large-v3 download alone took 281.7 s on the C: HDD and a second one blew the time box. Parakeet-via-ONNX throughput on this CPU is projected from a different processor and must be benchmarked before it is trusted.
  • Verified directly in installed source: the hotwords behaviour (faster_whisper/transcribe.py:1200), CTranslate2's supported compute types, the config-drift chain, and the live device selection.
